ML Monitor Vitals

A computer-vision prototype that reads vital signs directly off a photograph of a patient monitor using OCR, lets you verify each extracted value before it's recorded, builds a timeline as readings come in, and runs a simple ML trend classifier (improving / stable / worsening) over them.

Launch ML Monitor Vitals → Read the full technical reports →
Educational / research prototype — not for clinical decision-making. OCR confidence varies by monitor display and photo quality — always verify extracted values before use. The trend estimate is a prototype model output, not a clinical deterioration score.
How to use it

Manual

1

Photograph the monitor

Upload a photo of the patient monitor display. The system runs OCR over the image to extract heart rate, SpO2, blood pressure, respiratory rate, and EtCO2.

2

Verify each extracted value

Every extracted value comes with an OCR confidence score. Low-confidence readings (like blood pressure in the example, at 42% confidence) are flagged in red — check the OCR details and manually confirm or correct each value before it's added.

3

Add a verified reading to the timeline

Once you've confirmed the values, add the verified reading. Each reading builds a running patient timeline table and a multi-parameter trend chart (HR, SpO2, RR, EtCO2) over time.

4

Read the ML trend estimate

With enough readings in the timeline, the trend classifier estimates whether the patient's trajectory looks like it's improving, stable, or worsening, shown as a probability breakdown across the three classes. This is a directional estimate from a small prototype model, not a validated clinical risk score.

5

Check the clinical reference panel

Abnormal findings surface linked differential considerations — for example, a low SpO2 pattern lists possible considerations like ventilation impairment, pulmonary disease, or a measurement artifact. Reference only, not a diagnosis.

Written reports on ML Monitor Vitals
A Computer-Vision and Machine-Learning Prototype for Extraction, Verification, and Temporal Analysis of Physiological Vital Signs from Patient Monitor Images Technical prototype report
Abstract
Background

Patient monitors display multiple physiological measurements simultaneously, including heart rate, peripheral oxygen saturation, blood pressure, respiratory rate, and end-tidal carbon dioxide. Although these measurements are readily available on bedside monitoring equipment, transferring them into a digital record can require manual transcription. Optical character recognition (OCR) provides a potential mechanism for converting monitor photographs into structured physiological data.

Objective

This paper describes the design and implementation of an educational software prototype that uses computer vision, OCR, rule-based parsing, user verification, temporal visualization, and a machine-learning trend model to transform photographs of physiological monitors into structured vital-sign observations.

Methods

The application was implemented in Python using Streamlit for the interactive web interface, Pillow for image processing, regular expressions for structured blood-pressure extraction, Pandas for tabular data management, and Plotly for temporal visualization. The processing pipeline consists of five principal stages: image acquisition, OCR-based text extraction, physiological-value parsing, human verification, and longitudinal trend analysis. A specialized blood-pressure extraction pathway supplements general OCR because systolic and diastolic pressure are commonly represented as a paired numerical expression. Extracted measurements are assigned OCR-derived confidence values when available. Verified measurements are timestamped and stored in application session state. After at least three verified observations, a machine-learning model is invoked to estimate whether the recorded trajectory is improving, stable, or worsening. Rule-based clinical reference patterns are additionally generated from selected physiological thresholds.

Results

The implemented prototype provides an end-to-end workflow from monitor-image upload to structured vital-sign display, manual verification, longitudinal tabulation, visualization, and prototype trend classification. The system supports heart rate, SpO₂, systolic and diastolic blood pressure, respiratory rate, and end-tidal carbon dioxide. It also exposes OCR confidence information and provides rule-based reference considerations for selected abnormal physiological patterns.

Conclusions

The software demonstrates the feasibility of combining OCR, structured parsing, human verification, visualization, and machine-learning methods within a lightweight clinical-data interface. However, the implementation should be regarded strictly as a research and educational prototype. OCR errors, image quality limitations, parser assumptions, limited training data, absence of clinical validation, and potential distribution shift prevent the system from being interpreted as an autonomous clinical decision-support or diagnostic system.

Keywords: optical character recognition, computer vision, vital signs, physiological monitoring, machine learning, clinical informatics, human-in-the-loop systems, medical imaging, Streamlit

1. Introduction

Physiological monitoring is fundamental to the assessment of patients in emergency, prehospital, perioperative, and critical-care environments. Modern patient monitors commonly display several physiological variables simultaneously, including heart rate (HR), peripheral oxygen saturation (SpO₂), non-invasive blood pressure (NIBP), respiratory rate (RR), and end-tidal carbon dioxide (EtCO₂).

Despite the availability of these measurements in digital monitoring systems, photographs or screenshots of monitor displays are sometimes used for documentation, education, retrospective analysis, and software prototyping. Converting such images into structured data presents a computer-vision problem because the measurements are embedded within a graphical user interface rather than provided as machine-readable numerical data.

Optical character recognition provides a general mechanism for extracting textual and numerical information from images. However, physiological monitor displays introduce additional challenges. Multiple numerical values may be present simultaneously, labels may be separated spatially from their associated values, characters may be distorted by image perspective or illumination, and measurement formats may vary between manufacturers and device models.

The prototype described in this paper was designed to investigate a human-in-the-loop workflow in which OCR initially extracts candidate values, software parsing converts those candidates into structured physiological variables, and a human operator verifies the measurements before they are incorporated into a longitudinal timeline.

The architecture additionally incorporates temporal visualization and a machine-learning component intended to characterize the direction of recorded physiological trajectories. A rule-based reference layer provides contextual information regarding selected physiological patterns.

The primary design principle is therefore not autonomous interpretation, but automated extraction followed by human verification.

2. System Objectives

The prototype was developed around six functional objectives:

  • Accept a photograph of a physiological monitor.
  • Extract visible numerical information using OCR.
  • Convert OCR output into structured vital-sign variables.
  • Provide confidence information and allow manual verification.
  • Store verified observations as a time-indexed sequence.
  • Analyze and visualize temporal trends using statistical, rule-based, and machine-learning components.

The system was deliberately structured so that OCR-derived values were not automatically treated as verified clinical observations.

6. Optical Character Recognition
6.1 General OCR

After the operator activates the monitor-reading operation, the image is passed to the general OCR subsystem:

ocr_results = extract_text(image)

The application expects the OCR subsystem to return a list of structured objects. Each object is expected to contain at least a textual representation and an associated confidence value.

Conceptually, the OCR output can be represented as:

[

{

"text": "...",

"confidence": ...

},

...

]

The application includes defensive validation:

if not isinstance(ocr_results, list):

ocr_results = []

This prevents an unexpected OCR return type from propagating directly into later stages of the application.

The OCR results are retained in application session state:

st.session_state.ocr = ocr_results

This allows the extracted text and confidence values to remain accessible after the Streamlit application reruns.

7. Physiological Value Parsing

Following OCR extraction, the recognized text is passed to a dedicated parsing function:

vitals = parse_vitals(ocr_results)

The parser converts unstructured OCR output into a structured dictionary.

The expected variables include:

  • HR
  • SpO₂
  • systolic blood pressure
  • diastolic blood pressure
  • RR
  • EtCO₂

The parser is also treated defensively:

if not isinstance(vitals, dict):

vitals = {}

This establishes a clear boundary between the OCR subsystem and the user interface.

A conceptual representation of the resulting object is:

{

"hr": ...,

"spo2": ...,

"bp_sys": ...,

"bp_dia": ...,

"rr": ...,

"etco2": ...

}

The exact implementation of parse_vitals() is contained in the external parser module and therefore cannot be inferred completely from the provided interface code. Consequently, this manuscript describes the observable interface contract rather than assuming a specific internal parsing algorithm.

8. Specialized Blood-Pressure Extraction

Blood pressure receives an additional processing pathway.

This design is important because blood pressure is represented as a paired measurement rather than a single numerical value. The prototype therefore calls:

bp_results = extract_bp_candidates(image)

Candidate text is subsequently examined using a regular expression:

r"(\d{2,3})\s*[/\-]\s*(\d{2,3})"

This expression recognizes patterns such as:

120/80

120 - 80

The extracted components are interpreted as systolic and diastolic pressure.

The prototype then applies physiological plausibility constraints:

50 <= systolic <= 250

20 <= diastolic <= 150

systolic > diastolic

Candidates failing these criteria are discarded.

If multiple valid candidates are detected, the candidate with the highest OCR confidence is selected.

This creates a simple confidence-based candidate-selection mechanism:

9. Confidence Estimation

The application incorporates a confidence-display mechanism to communicate uncertainty associated with OCR extraction.

The find_confidence() function first searches for a parser-provided confidence value:

parser_confidence = vitals.get(

f"{vital_name}_confidence"

)

If a parser-specific confidence value is unavailable, the application searches the raw OCR results for a numerical match corresponding to the extracted vital.

For example, if the structured heart rate is 82, the algorithm examines OCR outputs for a numerical value matching 82 and retains the highest associated confidence.

For blood pressure, the function instead searches for OCR text containing a slash, reflecting the paired representation of the measurement.

The resulting confidence is classified into three presentation levels:

  • High: ≥ 0.80
  • Medium: 0.50–0.79
  • Low: < 0.50

These thresholds affect presentation only. They do not constitute experimentally validated probabilities of correct physiological extraction.

This distinction is important because OCR confidence is not necessarily equivalent to clinical correctness.

The interface includes several mechanisms intended to prevent malformed data from causing invalid displays or application failures.

The application's own labeling appropriately identifies this component as a prototype trend estimator rather than a validated clinical deterioration score.

15. Clinical Reference Layer

The application contains a rule-based reference subsystem that evaluates selected physiological measurements against predefined thresholds.

The implementation evaluates:

  • HR > 100 bpm
  • HR < 60 bpm
  • SpO₂ < 94%
  • systolic BP < 90 mmHg
  • RR > 20/min
  • EtCO₂ < 35 mmHg

When a threshold is met, the corresponding pattern is displayed along with a list of possible clinical considerations.

For example, an elevated HR triggers a "tachycardia pattern" containing possible considerations such as physiological stress, fever, hypovolemia, hypoxemia, medication effects, and cardiac rhythm disturbance.

These rules are implemented using straightforward conditional statements rather than a probabilistic diagnostic model.

For example:

if (

isinstance(hr_value, (int, float))

and hr_value > 100

):

The output is therefore better characterized as a rule-based clinical reference layer rather than an automated diagnostic system.

The application explicitly communicates that these considerations are not diagnoses.

17. Application State Management

Three principal state variables are initialized:

The supplied implementation does not show persistent database storage. Therefore, the history should be interpreted as session-level application state rather than a permanent medical record.

18. Error Handling

The principal image-processing workflow is enclosed in a try/except block.

If OCR, parsing, blood-pressure extraction, or another operation raises an exception, the interface reports the error rather than terminating the entire application.

Similarly, machine-learning execution is isolated within its own error-handling block:

try:

...

except Exception as e:

st.warning(

f"ML trend model unavailable: {e}"

)

This allows the core extraction and visualization workflow to remain usable if the optional trend-analysis subsystem fails.

19. Safety-Oriented Design

The prototype incorporates several safeguards intended to reduce inappropriate interpretation.

First, automated OCR values are explicitly presented as values requiring verification.

Second, the application separates extracted values from verified values.

Third, the machine-learning component is explicitly labeled as a prototype trend estimate.

Fourth, the clinical-reference layer is explicitly described as non-diagnostic.

Finally, the interface instructs users to compare extracted values with the original monitor and patient assessment.

These design decisions establish a decision-support boundary in which the software assists with transcription and visualization but does not replace clinical assessment.

20. Discussion

The implemented architecture demonstrates how multiple relatively simple computational components can be combined into an end-to-end physiological-data pipeline.

The first contribution is the integration of image-based extraction with structured physiological parsing. Rather than requiring manual transcription from every monitor photograph, OCR can provide candidate numerical values that are subsequently normalized into a predefined schema.

The second contribution is the use of a specialized blood-pressure extraction pathway. Blood pressure presents a different parsing problem because its two components must be identified together. Regular-expression matching and physiological plausibility filtering provide a lightweight mechanism for rejecting obviously inappropriate candidates.

The third contribution is the human-verification architecture. Instead of assuming OCR output is correct, the system explicitly inserts a human confirmation stage before measurements enter the longitudinal dataset. This is particularly important because OCR errors may result from glare, blur, image perspective, character segmentation, monitor typography, or overlapping graphical elements.

The fourth contribution is the integration of temporal visualization. Once measurements are verified, individual observations can be transformed into a time series, making changes in HR, SpO₂, RR, and EtCO₂ easier to inspect.

Finally, the prototype demonstrates how a machine-learning layer can be incorporated after data acquisition. However, the usefulness of such a model depends strongly on the quality, size, representativeness, labeling methodology, and validation of its training data.

21. Limitations

Several limitations should be considered.

21.1 OCR Performance

OCR accuracy is dependent on the quality of the input image and the underlying OCR implementation. The provided code does not specify the OCR engine, preprocessing operations, image segmentation strategy, character-recognition architecture, or benchmark performance.

Consequently, sensitivity and specificity for individual vital signs cannot be calculated from the interface code alone.

21.2 Monitor Variability

Different monitor manufacturers and models may use different fonts, layouts, colors, abbreviations, and numerical arrangements. A parser developed around one display configuration may therefore perform differently on another.

21.3 Blood-Pressure Parsing

The blood-pressure regular expression assumes a relatively conventional numerical representation. Alternative display formats may not be recognized.

The numerical plausibility constraints also prevent certain values from being selected even if they were correctly displayed by an unusual monitor configuration.

21.4 Confidence Interpretation

OCR confidence is used as a proxy for extraction reliability, but it should not automatically be interpreted as the probability that the physiological value is clinically correct.

21.5 Machine-Learning Validation

The machine-learning implementation is external to the supplied interface code. The training data, feature construction, model architecture, class definitions, cross-validation strategy, and independent test performance are not provided.

Therefore, no claims regarding model accuracy, sensitivity, specificity, calibration, generalizability, or clinical utility can be made from the supplied code.

21.6 Limited Temporal Data

The machine-learning component requires only three observations before producing an estimate. From a scientific perspective, three observations may provide very limited information about a physiological trajectory.

The minimum-observation requirement should therefore not be confused with evidence that three measurements are sufficient for reliable clinical trend prediction.

21.7 Lack of Persistent Clinical Storage

The supplied application stores historical measurements in Streamlit session state. No electronic health record integration, database layer, audit log, or durable patient-record mechanism is demonstrated.

21.8 Rule-Based Reference Thresholds

The clinical reference subsystem uses fixed numerical thresholds. Physiological interpretation can depend on age, baseline physiology, clinical context, treatment, environment, and measurement conditions. Consequently, threshold-triggered text should not be interpreted as individualized diagnosis.

22. Reproducibility and Future Evaluation

A rigorous evaluation of the prototype would require a dedicated dataset of monitor photographs with ground-truth annotations.

A suitable evaluation protocol could contain the following stages:

Stage 1: Image Dataset Construction

Collect monitor images representing different:

  • monitor manufacturers,
  • display layouts,
  • lighting conditions,
  • camera angles,
  • image resolutions,
  • patient-monitor configurations,
  • physiological value ranges.
Stage 2: Ground-Truth Annotation

Each image should be manually annotated for:

  • HR,
  • SpO₂,
  • systolic BP,
  • diastolic BP,
  • RR,
  • EtCO₂.

The ground truth should be independently verified against the original monitor output.

Stage 3: OCR Evaluation

Measure:

  • character-level recognition accuracy,
  • numerical recognition accuracy,
  • vital-sign extraction accuracy,
  • false-positive rate,
  • missing-value rate.
Stage 4: Parser Evaluation

Compare parsed values with ground truth and calculate variable-specific metrics.

Stage 5: Blood-Pressure Evaluation

Evaluate systolic and diastolic pressure independently and jointly, including cases containing visually ambiguous characters.

Stage 6: Human-in-the-Loop Evaluation

Measure the proportion of OCR outputs requiring manual correction and the time required to verify each observation.

Stage 7: Machine-Learning Evaluation

For the trend model, an independent dataset should be used for testing.

Potential metrics include:

  • accuracy,
  • precision,
  • recall,
  • F1 score,
  • confusion matrix,
  • calibration,
  • class-specific sensitivity,
  • temporal generalization.

Importantly, the test data should remain independent from the training data to prevent optimistic performance estimates.

23. Proposed Experimental Methodology

A formal study could compare three workflows:

Workflow A — Manual transcription

Monitor image → Human reads → Manual entry

Workflow B — OCR-assisted transcription

Monitor image → OCR → Human verification

Workflow C — Automated extraction

Monitor image → OCR → Parser → Automated record

Workflow B would be particularly informative because it reflects the architecture implemented in the prototype.

Primary outcome measures could include:

  • Time required to produce a verified vital-sign record.
  • Numerical transcription error rate.
  • Percentage of observations requiring correction.
  • Agreement between extracted and ground-truth values.
  • User-reported workload.

This experimental design would permit assessment of whether OCR assistance reduces transcription burden while maintaining human oversight.

24. Ethical and Clinical Considerations

A system processing physiological information must distinguish between technical extraction and clinical interpretation.

The prototype's architecture appropriately separates these functions. OCR identifies candidate information from an image; verification establishes the values that enter the historical record; visualization represents temporal data; and the reference layer provides possible contextual considerations.

None of these operations independently establishes a diagnosis.

Before deployment in clinical environments, additional considerations would include:

  • patient privacy,
  • secure image handling,
  • access control,
  • auditability,
  • data retention,
  • model validation,
  • clinical governance,
  • usability testing,
  • regulatory classification,
  • human-factors evaluation,
  • monitoring for systematic extraction errors.

In particular, performance should be evaluated across the diversity of monitor displays and clinical contexts in which the system is intended to operate.

25. Conclusion

This paper describes an educational prototype that combines computer vision, OCR, rule-based numerical parsing, human verification, temporal data visualization, machine-learning trend estimation, and clinical reference rules within a single Python-based application.

The principal engineering feature is the separation between automated extraction and verified clinical data. This approach recognizes that OCR output can contain errors and therefore should not automatically become part of a longitudinal physiological record.

The prototype demonstrates the technical feasibility of transforming photographs of physiological monitors into structured observations and subsequently analyzing those observations over time. Nevertheless, the current implementation does not provide evidence of clinical accuracy or clinical effectiveness. In particular, the OCR subsystem, parsing subsystem, and machine-learning model require independent validation before quantitative claims regarding performance can be established.

Accordingly, the system is best understood as a research and educational prototype illustrating the integration of computer vision and machine learning into physiological-data workflows rather than as an autonomous diagnostic or clinical decision-making system.

Clinical Potential and Implementation Manual for an Image-Based Physiological Monitoring Support System Clinical potential & implementation
Abstract

This manual describes the potential clinical applications, operational workflow, safety requirements, implementation considerations, and future development pathway for an image-based physiological monitoring support system capable of extracting vital-sign information from photographs of patient-monitor displays.

The system combines optical character recognition (OCR), numerical parsing, confidence estimation, human verification, temporal data visualization, prototype machine-learning trend analysis, and rule-based clinical reference information. Its primary potential clinical function is to reduce the burden associated with manual transcription of physiological measurements while creating a structured representation of monitor observations.

The system should initially be considered an assistive clinical-information technology rather than an autonomous diagnostic system. In a clinical environment, extracted measurements should remain subject to verification by appropriately trained healthcare personnel. The system should not independently determine diagnosis, treatment, disposition, or emergency intervention.

A staged implementation strategy is recommended, beginning with retrospective validation and simulated clinical workflows, followed by supervised prospective evaluation and only subsequently consideration of operational deployment. Clinical implementation should incorporate performance monitoring, cybersecurity and privacy controls, human-factors evaluation, documentation, governance, and applicable regulatory review.

1. Purpose

This manual describes the operation, testing methodology, and technical principles of a prototype machine-learning system designed to classify a set of physiological measurements into one of three demonstration categories:

  • Improving
  • Stable
  • Worsening

The system uses a Random Forest classification algorithm implemented with Python and scikit-learn.

The purpose of this prototype is to demonstrate a complete machine-learning workflow consisting of:

  • physiological data input,
  • feature extraction,
  • model training,
  • classification,
  • probability estimation, and
  • software testing.

Important: The model described in this manual is a demonstration prototype. Its training data and labels are synthetic and are not derived from a clinically validated dataset. Consequently, its output must not be interpreted as a clinical diagnosis, medical risk score, or validated prediction of patient deterioration.

2. System Overview

The prototype receives individual physiological readings containing up to six measurements:

FeatureDescription
HRHeart rate
SpO₂Peripheral oxygen saturation
BP SysSystolic blood pressure
BP DiaDiastolic blood pressure
RRRespiratory rate
EtCO₂End-tidal carbon dioxide

The measurements are converted into a standardized numerical feature vector:

[HR, SpO₂, BP Sys, BP Dia, RR, EtCO₂]

This vector is supplied to a trained Random Forest classifier.

The classifier returns:

  • a predicted category,
  • a confidence value, and
  • probability estimates for all three categories.

latest = history[-1]

1

2

0 → improving

1 → stable

2 → worsening

The Random Forest also produces probability estimates using:

model.predict_proba(features)

The results are converted into a dictionary:

{

"stable": ...,

"worsening": ...

19. Trend Analysis Limitation

Although the function is named:

predict_trend()

the current implementation does not mathematically calculate a temporal trend.

It uses:

latest = history[-1]

Therefore, only the most recent observation is supplied to the classifier.

For example, consider:

Reading 1: HR = 70

Reading 2: HR = 80

Reading 3: HR = 95

The current model receives only:

HR = 95

It does not explicitly calculate:

70 → 80 → 95

Consequently, the current implementation should technically be described as current-state classification, rather than a fully developed temporal trend model.

Scientific and Technical Manual
Vital-Sign Trend Classification Prototype

Version: 1.0 Date: September 2026 System Type: Educational machine-learning prototype Classification Task: Improving / Stable / Worsening

1. Purpose

This prototype was developed to demonstrate the use of a machine-learning classification pipeline for categorizing physiological observations into three predefined trend classes:

  • Improving
  • Stable
  • Worsening

The system uses six physiological features:

  • Heart rate (HR)
  • Oxygen saturation (SpO₂)
  • Systolic blood pressure
  • Diastolic blood pressure
  • Respiratory rate (RR)
  • End-tidal carbon dioxide (EtCO₂)

The prototype uses a Random Forest classifier implemented with Python and scikit-learn.

The system is intended for educational and technical demonstration purposes only. It has not been clinically validated and must not be interpreted as a clinical deterioration prediction system.
